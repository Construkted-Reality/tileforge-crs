## F1 — `to_ecef` silently returned `Ok([NaN, …])` for non-finite geographic input

Defect: proj4rs validates latitude but passes a non-finite **longitude** or **height**
straight through for geographic sources, so `to_ecef([NaN, 45, 0])` returned
`Ok([NaN, NaN, 4487348.408865919])` (RED evidence, verbatim). The identity (EPSG:4978)
short-circuit likewise copied `NaN` through. One poisoned vertex silently corrupts every
downstream bbox/centroid — the exact silent-corruption class this crate exists to prevent.

Fix: validate all three axes with `is_finite()` at the top of `to_ecef`, ahead of the
identity short-circuit, returning `CrsError::Reproject` naming the offending triple. Applies
uniformly to geographic, projected, and identity sources. Finite inputs are unchanged
(both parity grids stay <1 µm; identity stays bit-equal for finite input).

Test: `reproject::tests::non_finite_input_is_rejected` — folds in MT3 (each axis ×
{NaN, +inf, -inf} × {4326 geographic, 32617 projected, 4978 identity}), all assert `is_err()`.

Consumer grep (mesh + pc): all `to_ecef` call sites propagate the result via `?` /
`.map_err(...)`; none rely on the old `Ok(NaN)` pass-through. Safe to tighten Ok→Err.

## F2 — degenerate / non-finite ECEF origins silently accepted

Defect: proj4rs's geocentric inverse maps `[0,0,0]` to the north pole
(`Ok((0.0, 1.5707963267948966))`, review probe verbatim) and passes NaN through, so
`EnuFrame::from_ecef_origin` would anchor a whole tileset at the wrong place with no error
anywhere — the hardest failure mode to diagnose downstream. RED reproduced locally with the
guard disabled: `ecef_to_geodetic_lonlat([0,0,0])` returned Ok.

Fix: guard `ecef_to_geodetic_lonlat` (which `from_ecef_origin` calls first) against non-finite
input and against an implausibly small radius (`< MIN_ECEF_RADIUS_M = 6.2e6 m`; Earth's polar
radius is ~6.357e6 m, so any real surface anchor clears it). Both entry points now reject the
geocenter, deep-interior points, and non-finite origins with `CrsError::Reproject`.

Tests: `enu::tests::degenerate_or_non_finite_origin_is_rejected` (F2 RED→GREEN);
`ecef_to_geodetic_lonlat_recovers_known_lon_lat` + `basis_is_orthonormal_at_extreme_anchors`
fold in MT4 (direct value assert + poles/both-hemispheres/antimeridian coverage).

Consumer grep (mesh + pc): all `from_ecef_origin` / `ecef_to_geodetic_lonlat` call sites
propagate via `?` / `.map_err(...)`; none relied on the old degenerate pass-through.

## F6 — uppercase `.PRJ`/`.QPJ` sidecars silently ignored + doc self-contradiction

Defect: the module doc claimed the suffix lookup was "case-insensitive" then gave an example
showing `Foo.PRJ` is *not* found — a self-contradiction — and the code only probed lowercase
`.prj`/`.qpj`. A `FOO.PRJ` from legacy ESRI/Windows tooling next to `foo.ply` returned
Ok(None) on case-sensitive Linux, silently dropping georeferencing (the exact silent-loss the
module doc says must not happen). RED: `uppercase_prj_sidecar_is_found` panicked "must be
found" (returned None).

Fix (review option a): probe uppercase suffix variants too —
`SIDECAR_SUFFIXES = [".prj", ".PRJ", ".qpj", ".QPJ"]`, lowercase first so it keeps precedence.
Additive (finds strictly more files, no signature change). Rewrote the three drifted doc
comments to describe the actual behaviour.

Test: `sidecar::tests::uppercase_prj_sidecar_is_found`.

## F4 — `ecef_to_geodetic_lonlat` re-parsed two `Proj` objects per call (perf)

Defect: the function built EPSG:4978 and EPSG:4326 `Proj` objects from the proj4 catalogue on
every call (~1 µs/call per the review probe). Harmless today (only in-crate caller is
`from_ecef_origin`, once per dataset) but the function is `pub` and exported, so a consumer
calling it per-point on a 100M-point cloud would pay ~100 s of pure re-parsing.

Fix: hoist both into `LazyLock<Result<Proj, CrsError>>` statics, built once. Kept the error as
a stored+cloned `Result` (re-surfaced per call) rather than `.expect()`-panicking, matching the
crate's stated "propagate the tracing trail, don't panic" convention for these
compile-time-fixed codes. Behavior-identical: same outputs, same error path.

No new test (pure internal refactor). Proof: full suite stays 55-equivalent green, both frozen
PROJ parity grids <1 µm, and the four `EnuFrame` tests (which drive this path) pass unchanged.

## F5 + F7 — axis-order/unit contract doc + debug tripwire; stale parity-oracle comment

F5: `to_ecef`'s geographic input contract was undocumented — proj4rs wants GIS/proj4 order
`[lon_deg, lat_deg, h_m]`, but EPSG:4326's official axis order is lat,lon, so a careful caller
honouring EPSG order feeds `[lat, lon, h]` and gets silently-displaced output (the swap only
errors when `|lat-as-lon| > 90`). Documented the contract on `to_ecef` and in the `lib.rs`
Reprojector summary, and added a `debug_assert!(|lat| ≤ 90)` on the geographic path as a cheap
lon/lat-swap tripwire (`|lon| ≤ 180` deliberately not asserted — proj4rs wraps longitude).
Release behaviour unchanged; the F1 finite check runs first so the assert only sees finite input.

F7: `tests/parity_oracle.rs` claimed the `proj` crate "stays in `[dev-dependencies]`", but
`Cargo.toml` has no `[dev-dependencies]` at all and its NOTE forbids the libproj/SQLite3 FFI.
Reworded the comment to match reality (frozen cs2cs fixtures only; regenerate on a PROJ machine,
never reintroduce the FFI dep) so a future agent doesn't "restore" the forbidden dependency.

Docs/contract only (plus a debug-only assert); no new test. Full suite + both parity grids green.

## MT2 — US-survey-feet projected unit coverage (EPSG:2926)

Gap: no test exercised a non-metre projected linear unit, though state-plane US survey feet are
common in North American lidar. Added a single-point pin in `tests/reproject.rs`: EPSG:2926
(Washington State Plane North, `+units=us-ft`), input `[1266000, 230000, 0]` us-ft →
`[-2304729.212267, -3638457.830071, 4688531.713529]` ECEF, asserted <1 µm.

The expected ECEF was captured from proj4rs on .211 and **cross-validated** against the
closed-form WGS84 ellipsoid for the point's geographic position (lon −122.352°, lat 47.620°):
X/Y/Z match `N·cos·cos` / `N·cos·sin` / `N(1−e²)·sin` to 4+ sig figs, so it pins *correct*
unit handling, not merely self-consistent output. It is a regression pin (locks the us-ft path
against a proj4rs bump); the external frozen-cs2cs PROJ oracle for this point is MT1 (blocked).

Test: `us_survey_feet_source_to_ecef_matches_pin_within_1um`.
