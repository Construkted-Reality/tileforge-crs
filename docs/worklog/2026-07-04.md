# Worklog — 2026-07-04 (release 0.2.0)

Release-prep for `tileforge-crs` 0.2.0 (0.1.0 → 0.2.0, minor). Cuts the
review-remediation sprint (2026-07-02 review → 2026-07-03/04 fixes) into a
tagged-changelog release. No new code this day: version bump + CHANGELOG +
this note only. Per-finding RED/GREEN detail lives in
`docs/worklog/2026-07-03.md`; the review itself in
`docs/reviews/2026-07-02-comprehensive-code-review.md`.

## The arc

The 2026-07-02 comprehensive review read 100% of the crate (~1,582 src lines,
55 tests) and found **no critical or incorrect-math bugs** — a probe confirmed
geographic→ECEF matches closed-form WGS84 to 0.0 m, ENU orthonormality to
2.2e-16, and both frozen dual-hemisphere PROJ parity grids pass <1 µm. The
numerics were already solid.

What it found instead was a cluster of **silent-failure edges** — the exact
failure class a shared CRS core exists to prevent, where invalid input produces
plausible-looking wrong coordinates with no error anywhere:

- **F1** — `to_ecef([NaN, 45, 0])` returned `Ok([NaN, NaN, 4487348.4])` for
  geographic sources. proj4rs validates *latitude* but passes a non-finite
  longitude/height straight through. One poisoned vertex silently corrupts the
  whole tileset's bbox/centroid.
- **F2** — proj4rs's geocentric inverse maps `[0,0,0]` to the **north pole**
  (`Ok((0.0, 1.5707963…))`), so a zeroed centroid anchored a whole tileset at
  the wrong place, silently.
- **R2** (fresh-eyes review #2 follow-up) — F2's first guard only checked the
  *lower* radius floor; a ×1000 mm-as-metres scale error inflated the origin to
  ~6.4e9 m and still mapped to a valid-looking frame. Added the symmetric upper
  bound → accept range `[6.2e6, 6.6e6]` m (admits ~220 km altitude, rejects
  gross scale errors).
- **F6** — uppercase `.PRJ`/`.QPJ` sidecars were silently ignored on
  case-sensitive Linux, and the module doc *self-contradicted* (claimed
  case-insensitive, then showed an example that isn't found).
- **F5/F7** — undocumented `[lon,lat,h]` vs EPSG lat,lon axis-order hazard
  (documented + debug-only swap tripwire); stale parity-oracle comment
  referencing a `[dev-dependencies]` block that doesn't exist.
- **F4** — `ecef_to_geodetic_lonlat` re-parsed two `Proj` objects (~1 µs) per
  call; harmless today but a per-point trap for a `pub` export (hoisted to
  `LazyLock` statics).

Every fix was test-first (RED evidence captured verbatim before the change),
one commit per finding. Behaviour changes are all `Ok(invalid) → Err`
tightenings — a cross-consumer grep of mesh + pc-crs confirmed no call site
relied on the old pass-through.

Two test-only wins worth noting for their method: **MT1** was originally
flagged blocked (needs a cs2cs capture on a PROJ machine), but review #2's
insight was that for a **WGS84** source the transform is pure closed-form
geodetic↔geocentric on one datum — so an *independent* closed-form
implementation is definitional ground truth, not proj4rs-circular. That
unblocked the geographic oracle without any PROJ machine. **MT2** pinned a
US-survey-feet CRS (EPSG:2926) and cross-validated the expected ECEF against
the closed-form ellipsoid, so it locks *correct* unit handling, not merely
self-consistent output.

## Deferred (not in 0.2.0)

**F3 — GeoTIFF sentinel codes `0` / `32767`.** The review wanted the parsers to
reject sentinels (`parse_crs_string("EPSG:0")` currently returns `Ok(0)`).
Review #2 found `tileforge-pc` (`pc-crs/lib.rs:100-105`) **actively depends** on
that pass-through and calls `is_geotiff_sentinel` itself, so moving the error
site into the parser is a cross-consumer contract change awaiting Adrian's
sign-off. Held out of the release; the `is_geotiff_sentinel` detection helper
(shipped in 0.1.0) remains the consumer-side path.

## What shipped in 0.2.0

F1, F2, R2, F4, F5, F6, F7, plus tests MT1 (closed-form geographic oracle), MT2
(US-survey-feet), non-finite rejection, extreme-anchor ENU, and latitude /
pole-boundary pins. See `CHANGELOG.md`.
